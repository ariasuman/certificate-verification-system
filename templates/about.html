PROJECT NOTES

How the system works

A cloud computing demonstration of private object storage, document processing, and integrity verification.

Processing flow

  1. 01
    Validate and stage

    Uploads are limited to DOCX, PDF, PNG, JPG, or JPEG and 12 MB. The server uses a generated UUID in a private temporary directory and removes it when processing ends.

  2. 02
    Extract text

    python-docx reads paragraphs and tables. pdfplumber reads every PDF page and OCR is attempted on scanned pages. pytesseract and Pillow process image uploads.

  3. 03
    Store and register

    The original bytes are hashed with SHA-256 and uploaded to a private S3 bucket using SSE-S3. SQLite stores the expected hash and metadata separately from the file.

  4. 04
    Verify integrity

    Verification downloads the S3 object, hashes its current bytes, and compares that result to the registered expected hash using a constant-time comparison.

Integrity is not authenticity. Hash matching only indicates that bytes match a trusted reference. It does not validate the issuer, identity, or truth of a certificate. The expected hash is trustworthy only while its database record and host remain protected.

DEMO ACCESS

This first version has no user accounts or per-certificate authorization. Set DEMO_ACCESS_CODE to gate the entire demonstration, share it only with intended test users, and do not upload real or sensitive personal certificates. Use production identity and authorization before handling real records.

DEPLOYMENT NOTES

Choose a hosting option

Local development

Use a virtual environment, install requirements, set local values in .env, and install Tesseract OCR as an operating-system dependency.

Render web service

Deploy from Git with the included Procfile. Add environment variables in the Render dashboard. SQLite on Render's ephemeral filesystem is temporary; attach a persistent disk and point DATABASE_PATH into its mount, or use RDS/DynamoDB for durable records.

Amazon EC2

Install Python and Tesseract on the Linux instance. Attach an IAM instance role scoped to the application bucket; Boto3 uses the role automatically. Keep SQLite on a protected persistent volume or migrate it to RDS/DynamoDB.

AWS configuration: Keep S3 Block Public Access enabled and require encryption. On Render, use secure environment variables for an IAM user's limited access key pair; never commit them. On EC2, prefer an attached IAM role. Grant only the required bucket read/write actions and scope them to the application's bucket/prefix. For long-lived production metadata, migrate SQLite to Amazon RDS or DynamoDB.
